# Root-Key–Based Signing Architecture

## Purpose and Rationale

The system currently signs all API responses, including error responses, using Dilithium signatures wrapped in a SignedResponse protobuf. This already provides strong integrity and authenticity guarantees at the payload level.

However, once the public key itself is served over the API (via /api/keys/public) and is also wrapped in a SignedResponse, a trust bootstrap problem appears:
- A client cannot safely trust a public key that is only verified by itself.
- This creates circular trust and allows man-in-the-middle substitution of keys.

To solve this correctly, the system must introduce a root key that acts as a long-term trust anchor. This document describes the minimal architectural changes required to achieve that.

---
## Target Security Model (High Level)

The system will use two levels of Dilithium keys:

1. Root Dilithium Key
   - Long-lived
   - Highly restricted
   - Used only to sign other keys

2. Active Dilithium Key
   - Used to sign all normal API responses
   - Can be rotated without breaking clients

Clients trust responses by verifying signatures that ultimately chain back to the root public key, which is distributed out-of-band.

## Key Responsibilities

Root Key
- Exists before the application is deployed
- Private key stored securely (file, vault, HSM, etc.)
- Public key embedded in clients (Python, mobile, etc.)
- Used only to sign the active public key

Active Key
- Used by the application at runtime
- Signs all business responses and errors
- Can be regenerated or rotated
- Public part is distributed via /api/keys/public

## Required Architectural Changes

### 1. Introduce a Root Signing Component

Create a dedicated component responsible only for root signing.

Responsibilities:
- Load root private key at startup
- Provide a sign(byte[] payload) method

This component must never be used for normal API responses.

### 2. Formalize the Active Signing Component

You likely already have logic equivalent to this.

Responsibilities:
- Hold the active Dilithium key pair
- Sign all normal API payloads
- Expose the active public key for distribution

This key is considered replaceable and rotatable.

### 3. Split the SignedResponse Factory

Your existing SignedResponseFactory should be extended to support two signing paths:
- One method for signing with the active key
- One method for signing with the root key

Conceptually:
- wrapWithActiveKey(payload)
- wrapWithRootKey(payload)

This keeps signing intent explicit and avoids accidental misuse of the root key.

### 4. Update /api/keys/public Endpoint

The public key endpoint must:
- Build a PublicKeyResponse protobuf containing:
- Active Dilithium public key
- Algorithm identifier (e.g. DILITHIUM2)
- Key generation timestamp
- Wrap that payload using root-key signing, not the active key

This endpoint becomes a key distribution endpoint, not a normal business API.

### 5. Keep Existing Controllers and Advice Mostly Unchanged

Your current @RestControllerAdvice and controllers already enforce:
- Protobuf-only responses
- SignedResponse wrapping
- Consistent error handling

The only required change is ensuring they use active-key signing, not root-key signing.

No API contracts need to change.

## Trust Flow (End-to-End)
- Client starts with embedded root public key
- Client calls /api/keys/public
- Client verifies response using root public key
- Client extracts active public key
- Client verifies all other API responses using active public key

This flow eliminates circular trust and enables key rotation.

## Why This Design Is Necessary

Without this change:
- The system cannot prove the authenticity of its own public key
- Any network attacker could substitute keys
- Dilithium signatures would give a false sense of security

With this change:
- Trust is anchored outside the network
- Key rotation becomes safe
- Signature verification becomes meaningful
- The design aligns with established security models (similar to TLS root CAs, but simpler)

## What You Can Implement First

### Recommended implementation order:
1.	Generate and store a root Dilithium key pair
2.	Add a root signing component
3.	Split signing responsibilities in SignedResponseFactory
4.	Update /api/keys/public to use root signing
5.	Export root public key for client use

Client-side enforcement can be added once this foundation is in place.

## Scope Clarification

This design:
- Does not require TLS changes (though TLS is still recommended)
- Does not introduce certificates or PKI
- Does not affect protobuf schemas (except PublicKeyResponse, which already exists)

It strictly improves trust correctness without increasing system complexity unnecessarily.

---

## Summary

You are not changing what your system does — you are changing why it is trusted.

The introduction of a root key turns your signed-response mechanism from a local integrity check into a real, end-to-end trust model suitable for security-critical systems.
